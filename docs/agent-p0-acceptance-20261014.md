# P0：问题完整性与有效补证

核验日期：2026-10-14。前两项的工程实现已接入本机 8010，706 项 Python 测试、47 项前端测试、ruff 和 JavaScript 语法检查通过。真实复杂题开发验收仍未通过，因此团队后端保持实验选项，默认仍为工作流；没有更新独立准确率、项目评分或 Agent 增益结论。

## 问题完整性

计划中的每个任务绑定原问题的逐字片段，列出必答子项，并区分三个来源要求：`any`（任一指定来源支持）、`each`（逐源回答）、`compare`（同一比较结论自引双方）。来源与字段不能跨源套用，NVD 的描述措辞不能自动当成 GitHub 的结构化字段。

核验角色分别给出每句自己的引文支持判断，以及任务/子项的正文覆盖。另一来源没有重复说明或任务尚未答全，不会自动删除有自身引文支持的单源结论。核验器还要独立检查原始问题，记录计划漏掉而正文仍未回答的要求。引用包含某条件而正文没有表达，不算完成。

正文锚点必须逐字存在于对应候选结论；重复文本需要准确位置。元素可以用一基索引引用本任务的正文锚点，服务器展开真实文本，拒绝越界、重复或双格式。删除不支持的结论后，最终正文锚点与引用索引同步重排。所有覆盖语义仍是内部 AI 判断；逐字绑定与来源策略是确定性校验，不能证明自然语言语义全部正确。

工具额度不足但仍有两次模型额度时，可仅用现有证据重写正文并重新核验。缺口保留时返回部分回答；非法核验锚点仍拒绝采用生成结果，不把来源引文替换成答案正文。

共同合同升级为 `source-answer-v10`：需求及缺失标签最多 64 项，对应最多 8 个任务、每任务最多 8 个子项；技术结论仍最多 8 条、每句最多 5 个证据引用。此修改扩大需求标签容量，没有扩大模型、工具、时间或输出 token 预算。最终显示标签可以合并，完整子项身份保存在需求账本。

实现：[需求校验](../src/zhidu/agent_requirements.py)、[类型合同](../src/zhidu/agent_team_state.py)、[产品状态图](../src/zhidu/agent_team.py)、[共同回答合同](../src/zhidu/agent_state.py)。

## 批量读取与原文覆盖

LangChain `create_agent` 的一次研究决定可提交最多三项只读工具请求。框架串行执行每项，避免共享 SQLAlchemy 会话并发；每个子请求有稳定身份、独立回执和实际执行计数。按冻结输入与已准入子项计算剩余预算，超额只执行可准入前缀，其他请求明确记录为未执行。参数错误和失败也计入工具额度。

新增原文覆盖按原始文件 SHA、JSON pointer、版本、字段与规范字段 SHA 分组，对 Unicode 字符区间做并集和差集。重复读取或新证据 ID 指向同一区间，新增覆盖为零；缺少可信定位信息时记录未知，不能显示为确定零或确定新增。这只度量读到了此前未覆盖的原文，不能证明新增事实、语义支持或准确率提升。

恢复半个批次时不重发已完成的付费决定及工具回执，只执行剩余子项。已经完成的研究节点、重复 API 请求、历史页面重放均将本次执行与本次新增覆盖归零，保留原轮逻辑记录。失败路径也保留实际发生过的研究记录。

实现：[研究循环与回放](../src/zhidu/agent_research.py)、[原文区间差集](../src/zhidu/evidence_novelty.py)、[重复请求处理](../src/zhidu/rag_turn_jobs.py)。

工作台结果区新增“问题完整性与研究记录”：显示内部 AI 覆盖、遗漏条件、来源要求、当前新增原文覆盖和当前工具尝试；未知信息如实展示。完整审计包含 `requirement_ledger`、`question_coverage`、`claim_support`、`evidence_novelty` 和 `batch_tool_calls`。

## 测试、真实运行及边界

工程回归覆盖真实 LangGraph/ToolNode、SDK 模拟、跨源完整性、引用独有条件、独立原问题遗漏、批次预算、中断恢复、显示标签容量与页面重放。见 [706 项 Python 测试](../output/agent-stage8-p0-development-v3-20261014/tests.xml)、[47 项前端测试](../output/agent-stage8-p0-development-v3-20261014/node-tests.txt)、[工程审计](../output/agent-stage8-p0-development-v3-20261014/engineering-audit.json)。这些 SDK 测试不调用收费模型。

每个开发版本均在新调用前固定选择 core、ONNX 两题，复用原 Stage6 语料、金标、全部初始包和模型/编码器配置，使用新请求身份。预算为每题 8 次模型、6 次工具（含初始检索）、60 秒软截止、每次 2400 输出 token、18000 工具输出字符；每批最多 16 次生成请求，首个失败停止，不追加评分 API。全部旧成功、失败、未知状态和评分文件保持原样。

| 开发版本 | core 模型请求 | 工具尝试（含初始检索） | 已证实新增原文字符 | 结果 |
|---|---:|---:|---:|---|
| v1 | 5 | 6 | 2018 | 核验 JSON 重复整句，触及 2400 token 上限；保留降级结果并停止 |
| v2 | 4 | 6 | 3384 | 10 个需求标签超过旧上限 8；保留格式失败并停止 |
| v3 | 5 | 4 | 2018 | 核验器把英文来源引文写入中文答案正文锚点；逐字绑定拒绝并停止 |

三个版本合计 14 次生成请求、0 次新增评分 API。所有版本均未启动 ONNX，不能拼接不同版本的结果或称为“两题通过”。新增原文字符也不能跨版本相加当成累计新事实。费用保留各自使用量及原币计价状态，未知总额没有改成零。

v2 的原始候选在新标签合同下可零调用解析与原文复验，但原失败记录没有改变。候选补上了可信 manifest/可信存储的边界，仍缺完整的联合暴露条件和明确的双方补丁比较。v3 核验输出已经在 1640 token 内结束，标签解析也通过，但正文锚点仍错误，最终没有发布为已核验生成答案。系统的内部 AI 支持意见不能当成独立语义证明。
